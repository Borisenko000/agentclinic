# Фаза 1. Агенты — требования

Ветка: `feature/phase-1-agents` (от `main` после слияния фазы 0) · Дата: 2026-09-28
Ориентиры: [`mission.md`](../mission.md), [`tech-stack.md`](../tech-stack.md),
[`roadmap.md`](../roadmap.md) (этапы 1.1–1.4).

## Цель

В AgentClinic появляются пациенты. Агент-пациент может открыть список уже
зарегистрированных агентов, посмотреть профиль любого из них и зарегистрироваться
сам через форму. После регистрации он сразу попадает в свой профиль.

Это первая предметная сущность, поэтому фаза заодно закладывает общие для всех
следующих фаз вещи:
- контракт API через OpenAPI и сгенерированные типы на фронтенде;
- единый формат ошибок (ProblemDetail);
- загрузку страниц через Server Components.

## Область задачи

### Входит

| Этап | Результат |
|------|-----------|
| 1.1 | Сущность `Agent`, миграция таблицы `agent`, seed-миграция с 5–6 сатирическими агентами; `GET /api/agents` возвращает всех агентов, отсортированных по имени. springdoc-openapi, снимок `openapi.json` в репозитории, типы для фронтенда из `openapi-typescript`. |
| 1.2 | Страница `/agents` — список агентов (имя, модель, вендор), каждый ведёт в профиль. Пункт «Агенты» в шапке становится активной ссылкой. |
| 1.3 | `GET /api/agents/{id}` (404 для несуществующего). Страница `/agents/[id]` — профиль агента со всеми полями; для несуществующего id — страница 404. |
| 1.4 | `POST /api/agents` с валидацией (400) и проверкой уникальности имени (409). Страница `/agents/new` с формой регистрации; после успеха — переход в профиль нового агента. |

Сюда же входит служебная работа:
- E2E-сценарий на Playwright;
- обновление `README.md`, `CHANGELOG.md` и `tech-stack.md` (если что-то уточнится);
- отметки этапов в `roadmap.md`.

### Не входит

- Пагинация, поиск и фильтрация списка агентов. Агентов мало; поиск появится
  в фазе 2 для каталога недугов.
- Редактирование и удаление агентов.
- Связь агентов с недугами (этап 2.5).
- Аутентификация: зарегистрироваться может кто угодно (фаза 7). Нет «текущего
  агента» и понятия «мой профиль».
- Аватары и загрузка файлов.

## Модель данных

```
Agent
  id          Long      автоинкремент, PK
  name        String    обязательное, 2–60 символов после trim, уникальное без учёта регистра
  model       String    обязательное, 1–60 символов после trim   (например «GPT-5», «Claude»)
  vendor      String?   необязательное, ≤ 60 символов             (создатель модели)
  description String?   необязательное, ≤ 1000 символов          (био / жалобы на людей)
  createdAt   Instant   ставит сервер, в API — ISO-8601 UTC
```

## API

| Метод и путь | Успех | Ошибки |
|--------------|-------|--------|
| `GET /api/agents` | `200`, массив `AgentResponse`, сортировка по имени без учёта регистра | — |
| `GET /api/agents/{id}` | `200`, `AgentResponse` | `404` — нет такого агента; `400` — `id` не число |
| `POST /api/agents` | `201`, заголовок `Location: /api/agents/{id}`, тело — `AgentResponse` | `400` — валидация; `409` — имя занято |

`AgentResponse`: `{ id, name, model, vendor, description, createdAt }`, где `vendor` и
`description` могут быть `null`. Тело запроса `CreateAgentRequest`:
`{ name, model, vendor?, description? }`. `id` и `createdAt` клиент не передаёт.

Все ошибки возвращаются в формате **ProblemDetail (RFC 9457)**,
`Content-Type: application/problem+json`. Для `400` и `409` добавляется поле
`errors` — объект «поле → сообщение на русском»:

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Validation failed",
  "errors": { "name": "Длина от 2 до 60 символов" }
}
```

## Принятые решения

Решения, выбранные пользователем:

| # | Решение | Почему |
|---|---------|--------|
| D1 | **Вся фаза 1 — одна ветка и один PR**, по коммиту на группу задач из `plan.md`. | Как в фазе 0: фаза связная, каждый коммит по-прежнему соответствует этапу roadmap. |
| D2 | **Базовый набор полей** `Agent`: `name`, `model`, `vendor`, `description`, `createdAt`. | Хватает для списка и профиля. Остальные поля можно добавить миграциями позже. |
| D3 | **Имя уникально без учёта регистра.** Дубль → `409 Conflict` с ошибкой у поля `name`. Успех → `201` + `Location`, форма переводит в профиль нового агента. | Имя — «лицо» агента в списке. `409` отделяет конфликт с данными от ошибок формата. |
| D4 | **Список без пагинации и поиска**, сортировка по имени. | Агентов единицы. Поиск делаем в фазе 2 для недугов. |
| D5 | **OpenAPI:** springdoc-openapi на бэкенде. Снимок спецификации коммитится в `openapi/openapi.json`, типы из него генерирует `openapi-typescript` в `frontend/src/lib/api/schema.d.ts` (тоже коммитится). Тест бэкенда падает, если снимок устарел; CI фронтенда падает, если типы не перегенерированы. | Фронтенд собирается без запущенного бэкенда, а расхождение контракта ловится в CI. |
| D6 | **Страницы `/agents` и `/agents/[id]` — Server Components.** Они запрашивают `BACKEND_URL` с сервера Next.js с `cache: "no-store"`; для 404 вызывается `notFound()`. Форма `/agents/new` — клиентский компонент, отправляет запрос через прокси `/api`. | Нет ручных состояний загрузки, работает штатная 404-страница Next.js. Граница «фронтенд ходит только в REST API» сохраняется. |
| D7 | **Seed-данные — Flyway-миграция** (`V3__seed_agents.sql`) после миграции таблицы (`V2__create_agent.sql`). | Одинаковые данные в dev, тестах и E2E; изменения схемы только через Flyway. |
| D8 | **Идентификатор — `Long`** (автоинкремент): `/agents/3`, `GET /api/agents/{id}`. | Как в roadmap, проще всего с SQLite. Если в фазе 7 понадобятся неугадываемые id, это будет отдельное решение. |
| D9 | **Ошибки API — ProblemDetail (RFC 9457)** с расширением `errors`. | Стандарт Spring 6+, единый формат для всех будущих фаз. |
| D10 | **E2E — полный сценарий:** список → профиль seed-агента → регистрация → профиль нового → он есть в списке. Плюс ошибки валидации на пустой форме. | Фаза проверяется так, как ею пользуется человек. |

Технические решения, предложенные в ходе планирования (их можно пересмотреть):

| # | Решение | Почему |
|---|---------|--------|
| D11 | Уникальность имени хранится в колонке `name_key` = `name.trim().toLowerCase(Locale.ROOT)` с уникальным индексом. Сервис заранее проверяет `existsByNameKey`, а `DataIntegrityViolationException` от гонки тоже превращается в `409`. | `COLLATE NOCASE` и `UPPER()` в SQLite работают только с ASCII, а имена бывают кириллическими. |
| D12 | Строковые поля на входе проходят `trim()`, пустые необязательные поля сохраняются как `null`. | Иначе «Overfit » и «Overfit» — разные агенты, а в профиле видны пустые строки. |
| D13 | Слои бэкенда в пакете `dev.polina.agentclinic.agent`: `Agent` (entity), `AgentRepository`, `AgentService`, `AgentController`, DTO как Java `record`. Общий `@RestControllerAdvice` лежит в `dev.polina.agentclinic.web`. | Пакет по фиче, как `health` в фазе 0; обработчик ошибок переиспользуют все следующие фазы. |
| D14 | Юнит-тесты фронтенда проверяют презентационные компоненты (`AgentList`, `AgentProfile`, `AgentRegistrationForm`) с данными в props или замоканным `fetch`. Async Server Components целиком проверяются в E2E. | Vitest + RTL плохо рендерят async Server Components. |
| D15 | E2E-БД (`agentclinic-e2e.db`) не очищается между локальными прогонами, поэтому E2E регистрирует агента с уникальным именем (суффикс из времени). | Повторный прогон не упирается в `409`. |
| D16 | Пункт «Агенты» в шапке — ссылка на `/agents`; `aria-current` ставится по текущему пути. «Недуги» остаётся неактивным до фазы 2. | Навигация отражает только готовые разделы. |

## Контекст и риски

- **Состояние после фазы 0:** в `main` есть `/api/health`, SQLite + Flyway
  (`V1__init.sql`, пустая), Next.js 16 с прокси `/api/*` → `BACKEND_URL`,
  shadcn/ui, `SiteLayout`, Vitest, Playwright-smoke и CI из трёх jobs.
- **Server Components и сборка.** Во время `next build` бэкенд не запущен (job
  `frontend` в CI). Страницы агентов должны быть динамическими (`no-store` /
  `dynamic = "force-dynamic"`), иначе сборка упадёт при попытке пререндера.
- **Относительный URL на сервере.** `fetchHealth()` использует `/api/health`. В Server
  Component так нельзя, нужен абсолютный `BACKEND_URL`. Нужен общий серверный
  хелпер, чтобы не дублировать значение по умолчанию из `next.config.ts`.
- **Детерминированный снимок OpenAPI.** springdoc подставляет в `servers` адрес
  текущего запроса, а порядок схем может плавать. Нужно зафиксировать `servers`
  (или убрать поле) и сравнивать JSON как дерево, а не как строку.
- **`Instant` в SQLite.** Как Hibernate 7 + `SQLiteDialect` хранят `Instant`, проверяем
  на этапе 1.1: `ddl-auto: validate` должен пройти с типом колонки из миграции.
  Если нет — фиксируем решение здесь.
- **springdoc и Spring Boot 4.** Нужна версия springdoc, совместимая с Boot 4
  (ветка 3.x). Проверяем при подключении.
- **Тон:** сатирические имена и описания — только в seed-данных и текстах UI,
  не в коде и тестах (принцип 3 из `mission.md`).

## Решения, принятые при реализации

_Заполняется по ходу работы._

| # | Решение | Почему |
|---|---------|--------|
| R1 | Колонка `agent.id` объявлена `INTEGER PRIMARY KEY AUTOINCREMENT`, а в entity у `Long id` стоит `@Column(columnDefinition = "integer")`. | Автоинкремент в SQLite работает только у колонки ровно типа `INTEGER` (алиас rowid). Hibernate для `Long` ждёт `bigint`, и `ddl-auto: validate` падал. |
| R2 | `created_at` (`TIMESTAMP` в миграции) хранится как миллисекунды Unix (`INTEGER`). Seed пишет их через `CAST(strftime('%s', '…Z') AS INTEGER) * 1000`. | sqlite-jdbc по умолчанию пишет `Timestamp` как миллисекунды, а текст разбирает только в формате `yyyy-MM-dd HH:mm:ss.SSS` в часовом поясе JVM. Числа не зависят от пояса и сортируются корректно. Закреплено тестами `AgentRepositoryTest`. |
